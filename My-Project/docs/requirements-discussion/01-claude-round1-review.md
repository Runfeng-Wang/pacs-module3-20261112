**传输语法 [P]**：接受 Implicit VR LE（1.2.840.10008.1.2）、Explicit VR LE（…1.2.1），以及常见压缩语法（JPEG Baseline …1.2.4.50 —— 内镜常用，JPEG Lossless …4.70，JPEG 2000 …4.90 / .91，RLE …1.2.5），**一律原样保存、不转码**。像素哈希对压缩数据按封装字节计算，不需要解码器。

**C-FIND 匹配能力 [P]**（在一致性声明中写明）
- 层级：PATIENT / STUDY / SERIES / IMAGE；只支持分层查询，不支持关系查询。
- 键：PatientID、PatientName、PatientBirthDate、PatientSex；StudyInstanceUID、StudyDate、StudyTime、AccessionNumber、StudyID、StudyDescription、ModalitiesInStudy、NumberOfStudyRelatedSeries / Instances；SeriesInstanceUID、Modality、SeriesNumber、NumberOfSeriesRelatedInstances；SOPInstanceUID、SOPClassUID、InstanceNumber。
- 匹配方式：单值、通配符（`*` `?`）、日期 / 时间范围、UID 列表、空值（通用匹配）。
- 字符集：支持 Specific Character Set 为默认、ISO_IR 192（UTF-8）、GB18030，用合成中文姓名测试。
- 支持 C-CANCEL。

**状态码 [P]**（标"核实"的要在实现时对照 pynetdicom 3.x 和 PS3.4 / PS3.7 确认）

| 情形 | 状态 |
|---|---|
| 存储成功（已持久化） | 0x0000 |
| 存储资源不足 / 写盘失败 | 0xA700（Out of Resources） |
| 数据集与 SOP 类不符 | 0xA900 |
| 缺必需 UID、UID 与命令不一致、无法解析 | 0xC000–0xCFFF 内的具体码，并附 ErrorComment（≤64 字符） |
| 同 UID 不同内容（冲突） | 暂定 0x0111（Duplicate SOP Instance，PS3.7 通用状态）**核实**；不可用时改用 0xCxxx + ErrorComment |
| 已登记对端越权操作 | 暂定 0x0124（Refused: Not Authorized）**核实**；否则用 0xCxxx |
| C-MOVE 目的地未登记 | 0xA801（Move Destination Unknown） |
| C-MOVE / C-GET 子操作中有失败 | 0xB000，附 Failed SOP Instance UID List（0008,0058） |
| C-FIND / C-MOVE / C-GET 进行中 / 被取消 | 0xFF00 / 0xFE00 |

**C-STORE 实现方式对比（为 Week13 预留）[P]**
- 方案 a：`event.dataset` 解码后用 pydicom 重新写文件。实现简单，但可能改变字节（长度编码、VR、私有标签），**会破坏"与上传时一致"**。
- 方案 b（推荐）：`event.encoded_dataset()` 取接收到的原始编码字节，前面加上 File Meta 后写文件。**字节保真**，哈希基线可以直接对应"上传时"。
- 方案 c：解码并规范化存储（统一 Explicit VR LE）。方便显示，但违反字节一致，不采用。

### 5.2 白名单身份边界
- **身份要素 [P]**：Calling AE Title（去掉首尾空格后精确匹配，区分大小写）+ 源 IP（精确 IP；CIDR 是否允许待确认 Q-I4）+ 启用状态。被叫 AE（Called AE）必须等于 B 的 AE Title。
- **角色 [P]**：`STORE`（可发 C-STORE）、`QUERY`（C-FIND）、`RETRIEVE`（C-MOVE / C-GET 请求方）、`MOVE_DEST`（可作为 C-MOVE 目的地，必须登记 host:port）。所有已登记对端都可以 C-ECHO。
- **拒绝方式 [P]**
  - 未登记 AE、AE 与 IP 不符、条目停用：A-ASSOCIATE-RJ（result=1 permanent，source=1 service-user，reason=3 calling-AE-not-recognized）。
  - 被叫 AE 错误：reason=7。
  - 以上都审计并告警；同一来源 60 秒内的重复拒绝聚合成一条告警（防刷屏）。
- **C-MOVE 目的地 [P]**：目的地的地址和端口**只从白名单读取**，不信任请求方提供的地址。未登记的目的地返回 0xA801 并告警，这对应课程示例"未授权导出原始影像必须报警"。
- **维护 [P]**：通过 GUI 和 CLI 增删改、启停；校验 AE Title（1–16 字符、无反斜杠、无控制字符、不能全为空格、唯一）、IP 和端口合法；变更对**新关联**立即生效，进行中的关联跑完为止；变更审计记录前后值。
- **边界（写入需求文档）**：白名单只是**准入控制，不是认证**。同一网段内可以伪造 AE + IP；没有 TLS 就不保证传输机密性和完整性。本机回环测试时所有对端都是 127.0.0.1，"IP 不符"用例的做法是：把 AE 登记为 10.0.0.5，再从 127.0.0.1 连接（不依赖多网卡）。
- **实现风险（核实）**：pynetdicom 自带的 `require_calling_aet` 只有静态 AE 列表，不含 IP，也不能动态更新。要找到关联请求的正式拦截点，或做一个受控子类，**必须发出真正的 A-ASSOCIATE-RJ**，不能用 A-ABORT 冒充拒绝。测试时抓取拒绝的 result / source / reason 做断言。

### 5.3 并发与验收阈值
客户没给数量 [Q-I1]。我提议以下**实验参数**，它们不是医院 SLA [P]：

| 用例 | 输入 | 通过判据 |
|---|---|---|
| CC-1 并发接收 | 4 个存储 SCU 同时发送：CT_SIM_1 / CT_SIM_2 各 100 张 512×512×16bit CT；ENDO_SIM_1 / ENDO_SIM_2 各 25 张 640×480 RGB VL 内镜。共 250 个实例，约 150 MB | 250 个 0x0000；库内恰好 250 条且无重复；每个实例的数据集哈希与发送端一致；服务端无未处理异常；审计条目数与操作对应 |
| CC-2 并发收取 | CC-1 进行时，WS_SIM_1（C-FIND + C-MOVE）和 WS_SIM_2（C-FIND + C-GET）各对预置的 100 张检查重复 3 轮 | 每轮子操作完成数 = 100、失败数 = 0，收到的文件哈希与基线一致；负载期间 C-ECHO 响应 < 2 秒 |
| CC-时间 | CC-1 + CC-2 | 总耗时 ≤ 300 秒（宽松硬门槛，只为防止挂死），实际耗时如实记录作为基线 |
| CC-3 超限 | 测试配置 `max_associations=8`，同时发起 9 个关联 | 第 9 个被 A-ASSOCIATE-RJ（transient，local-limit-exceeded，**拒绝码核实**）；前 8 个不受影响；服务不崩溃；拒绝被审计；释放后重试成功 |
| CC-4 同 UID 竞争 | 2 个 SCU 同时发送同一 SOP Instance UID：(a) 内容相同；(b) 内容不同 | (a) 两个都成功，库内 1 条；(b) 恰好 1 个成功、1 个冲突失败，库内为先提交者，冲突对象进隔离区并告警 |

默认生产配置 `max_associations=20`（可配置）[P]。真实医院的峰值设备数、单检查张数（薄层 CT 可达上千张）和延迟期望都待确认。

### 5.4 重复 UID 与冲突
| 情形 | 判定 [P] | 系统行为 |
|---|---|---|
| 同 SOP Instance UID，数据集字节哈希相同（设备超时重发） | 正常（幂等） | 返回 0x0000，不重复入库，审计 `duplicate-identical` |
| 同 SOP Instance UID，内容不同 | 异常 / 视条件而定 | 拒绝（D7）；原文件和基线不变；冲突对象存入隔离区供取证；告警 `uid-conflict`（含两份哈希和差异字段） |
| 同 Study / Series UID 下追加新实例 | 正常 | 归入原检查 / 序列 |
| 不同 Study UID 下出现同一 Series UID | 数据异常 | 拒绝或警告待确认，本期**拒绝**并写明原因（DICOM 要求 Series 隶属唯一 Study）[P] |
| 同 PatientID 但姓名 / 生日不同 | 数据质量问题，不算篡改 | 接收，归到同一患者，界面标注"人口学信息不一致"（不告警）[P]，Q-R2 |
| 不同 PatientID、同姓名 | 正常 | 不合并 |

说明：DICOM 规定像素变化必须换新 SOP Instance UID，所以"同 UID 不同内容"在协议上本来就不合规，拒绝有依据。

### 5.5 落盘成功 / 失败语义
- **成功定义 [P]**：只有以下步骤全部完成，才返回 0x0000：
  1. 原始编码字节加上 File Meta，写入临时文件。
  2. `fsync`。
  3. 读回并复算哈希（读回校验，可配置，原型默认开启）。
  4. 原子重命名为正式路径。
  5. 在**同一数据库事务**中写入实例索引、基线和审计，然后提交。
- **失败处理**：任一步失败都返回失败状态，删除临时文件或已重命名的文件，不留索引记录，产生"存储失败"告警（系统故障类，不算篡改）。
- **崩溃恢复**：启动时对账。磁盘上有文件但没索引（孤儿文件）就移入隔离区并告警；有索引但没文件就记"文件缺失"并告警。
- **故障注入**：通过配置或测试钩子模拟"写文件失败""数据库提交失败"，这样可以自动化验证，不依赖真的把磁盘写满。
- **存储布局**：`store/<yyyy>/<mm>/<dd>/<内部ID 或 sha256(SOPInstanceUID)前 32 位>.dcm`，避开 Windows 260 字符路径上限（K12）。

### 5.6 完整性基线及其信任边界
**基线内容（每个实例）[P]**
1. `file_sha256`：整个 Part-10 文件的哈希。
2. `dataset_sha256`：接收到的编码数据集字节（不含 File Meta）的哈希，这就是"上传时"的指纹。
3. `pixel_sha256`：(7FE0,0010) 的原始值字节哈希；封装压缩数据按全部片段计算。
4. 完整非像素元数据快照（JSON，去掉大块二进制），其中标注"关键字段"（PatientID / Name / BirthDate / Sex、各级 UID、StudyDate / Time、AccessionNumber、Modality、InstanceNumber、Rows / Columns、Bits*、PhotometricInterpretation、PixelSpacing、SliceThickness、Rescale*、ImagePosition / Orientation、Manufacturer、StationName 等）。
5. 来源 AE / IP、关联 ID、接收时间、传输语法、文件大小。
6. P1：像素分块哈希（未压缩数据按帧和 32×32 像素块计算；压缩数据按帧或片段），用于报告"变化位置"。
7. 基线行用 HMAC-SHA256 保护；密钥文件放在数据目录之外的 `runtime/keys/`。

**核查分类 [P]**
- 文件缺失
- 无法解析
- 像素数据变化（P1：附变化块范围）
- 元数据变化（列出标签、名称、前值 → 后值，区分关键 / 非关键）
- 仅文件结构变化（像素和元数据都相同，File Meta 或编码变了）
- 索引与基线不一致（数据库中的患者 / 检查字段被改）
- 基线记录被篡改（HMAC 不符）
- 审计链断裂

**信任边界**
```
[设备/工作站] --TCP 明文, AE+IP 声称身份--> [B 关联层: 白名单] --> [B 接收: 计算基线, 原样落盘]
                                                                   |
                                                   [文件存储] [SQLite: 索引/基线(HMAC)/审计(哈希链)]
                                                        ^ 威胁: 有文件系统/数据库写权限的人或程序
                                                   [HMAC 密钥文件, 数据目录外] <- 信任锚(同机, 弱)
```
- B **信任**：自己的进程；接收完成那一刻已登记设备发来的字节（作为基线）；密钥文件。
- B **不信任**：之后的文件和数据库状态，所以要核查。
- B **不能保证**：入库前数据的真实性（设备端或传输途中被改）；能同时改数据、改数据库又拿到密钥的管理员级攻击者；篡改者身份；两次扫描之间的实时发现。

### 5.7 告警与审计
**告警记录 [P]**：ID、时间、级别（高 / 中 / 低）、类型、对象标识（患者 / 检查 / 序列 / 实例或对端 AE / IP）、详情（变化类别、字段、前后值）、建议处置、状态（未处理 / 已确认）、确认人、确认时间。管理界面显示红色计数和列表；确认动作记入审计。不对外推送。

**哪些事件告警、哪些只审计 [P]**

| 告警（高） | 告警（中） | 只审计（不告警） |
|---|---|---|
| 完整性异常（像素 / 元数据 / 缺失 / 不可解析 / 索引或基线被改） | 未登记 AE、AE 与 IP 不符、停用条目来连接（聚合） | 正常关联、ECHO、STORE、FIND、MOVE、GET |
| 未授权检索 / 未登记 C-MOVE 目的地（未授权导出） | UID 冲突重发 | 相同实例重发（幂等） |
| 审计链断裂 | 存储失败（系统故障） | 设备断连、重连（课程原文："不算事故"）|
| 调阅时发现篡改并已阻断 | 启动对账发现孤儿文件 | 白名单维护、服务启停、核查运行、告警确认 |

**审计记录**：时间（UTC + 本地）、事件类型（对齐 DICOM / IHE 审计事件名，如 *DICOM Instances Transferred*、*Query*、*Security Alert*、*Application Activity*，便于以后迁移 ATNA）、行为者（对端 AE / IP，或本机操作员）、对象（UID）、结果、详情。每行含上一行的哈希，构成哈希链。界面不提供修改或删除入口，可校验、可导出 CSV / JSON。

**操作员身份 [P]**：GUI 没有登录系统，记录"操作系统用户名 + 启动时自填的操作员名"，并明确这**不是认证**。GUI 登录和 RBAC 本期不做，Q-I6。

| 工作站正常查询、调阅 | 正常 | 库内文件不变，只审计 |

### 5.9 异常结果与系统边界（模块二 3.5）
**一句话**：系统发现异常时，应输出**患者 ID / 检查 UID / 序列 UID / 实例 UID、变化类别（像素 / 元数据 / 文件 / 索引 / 基线 / 审计）、变化的字段（标签与名称）或位置（P1：像素块范围）、前后值、检测时间、该实例最后一次经系统记录的合法操作（来自审计）以及文件修改时间（标注"来自操作系统，不可信"）、建议处置**，以便**信息科管理员或质控人员**能够**确认影响范围、隔离或恢复该实例，并追查访问记录**。

**本系统能做到**
1. 发现入库后库内文件任何字节的变化，并区分像素、元数据、结构变化。
2. 发现数据库索引、基线记录和审计记录被改动。
3. 拒绝未登记或越权的对端，并记录、告警。
4. 只在数据真正持久化后才向设备确认成功。

**本系统不能据此保证**
1. 入库前的数据真实、正确（例如设备录错患者，或传输途中被改）。
2. 确定是谁篡改。
3. 防御同时控制数据目录、数据库和密钥的管理员级攻击。
4. 防止 AE / IP 伪造（没有 TLS）。
5. "指纹一致"只说明与入库时相同，不说明临床事实真实。
6. 在两次扫描之间实时发现（调阅时一定会校验）。

## 9. 互联协议说明草案（对端照文档即可对接）[P]
将来在 `My-Project/docs/` 输出，结构参照 DICOM PS3.2 一致性声明。

1. **实现概要**：B 是单个 AE。默认 AE Title `PACS_B`，端口 11112（两者都可配置）。监听地址默认 127.0.0.1；跨组联调时改为局域网地址，并需要用户自行放行 Windows 防火墙（本期不改系统设置）。
2. **B 作为 SCP 支持的 SOP 类与传输语法**：§5.1 表格。表示上下文接受规则：每个抽象语法按"原样优先"选传输语法。
3. **B 作为 SCU（C-MOVE 子操作）**：向目的地提议存储类，提供存储时的传输语法和 Implicit / Explicit VR LE。
4. **C-FIND 键表、匹配规则、字符集**：§5.1。
5. **准入登记流程**：对端须提供 AE Title、IP、角色，作为 C-MOVE 目的地时还要提供端口；由 B 管理员登记后才能连接。拒绝时返回的 RJ 参数见 §5.2。
6. **成功 / 失败的确认方式**（这是课程点名的难点）
   - A → B：每张图像的 C-STORE 响应为 0x0000，即表示**已持久保存并建立基线**；失败码及含义见 §5.1 表，ErrorComment 给出原因。设备收到非 0x0000 应重发或报错。
   - B → C：C-FIND 以 0xFF00 逐条返回、0x0000 结束；C-MOVE / C-GET 返回子操作的完成、失败、警告计数，失败的 UID 放在 (0008,0058)。C 端要以"完成数 = 期望数且失败数 = 0"作为调阅成功的判据。
7. **超时与限制**：ACSE 30 秒、DIMSE 60 秒、网络 60 秒（暂定）；最大 PDU 默认 16384（暂定，可配置）；最大关联数 20。
8. **已知限制**：无 TLS；不支持关系查询；不转码存储；不提供 Storage Commitment（待确认）。
9. **跨组联调清单**：A→B echo / store（CT、内镜 / SC）；B→C find / move / get；异常项（未登记、错误被叫 AE、未登记目的地）；联调记录模板（时间、双方 AE / IP / 版本、用例、结果、截图 / 日志）。**状态写明：未执行，待 week15**。

## 13. 风险、工作量与分期
**主要技术风险（实现时第一时间验证）**
1. pynetdicom 动态准入拦截点（§5.2）。
2. C-MOVE / C-GET 能否按原样字节发送（库函数是否接受文件路径或原始数据，否则要解码再编码）。
3. 拒绝码和各状态码在库中能否使用（0x0111 / 0x0124 / 超限拒绝）。
4. Windows 上 fsync 和并发写的性能。
5. 可重复地注入传输中断。
6. PyQt5 wheel 与所选 Python 版本是否兼容。

**工作量判断**：P0 的量不小（DICOM 服务 5 类、准入、存储、完整性、告警审计、模拟器、约 40 个以上正反用例、并发测试、文档、OpenSpec 产物，再加最小 GUI）。在共享的 5 小时额度内**有可能完成，但很紧**，所以要严格按里程碑推进，确保每个里程碑结束时交付物都能自洽：
- M1：工程骨架、配置、数据库、审计链、白名单准入加 ECHO（含 RJ 测试）。
- M2：STORE（落盘语义、重复冲突、基线）。
- M3：FIND / MOVE / GET。
- M4：完整性核查、调阅前校验、告警。
- M5：并发用例、演示脚本、接口文档、需求文档定稿。
- M6：最小 PyQt5 控制台加离屏冒烟测试。
- M7：P1 项。

如果额度紧张，砍 M7，并压缩 M6 的页面数量，**不砍**协议的真实性和正反用例。
