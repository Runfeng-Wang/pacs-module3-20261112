## B. 安全与信任边界（设计上的限制，不是 bug）
1. 白名单基于 AE Title + 源 IP，**不是认证**。同网段可以伪造；本期没有 TLS。
2. HMAC 密钥（`runtime/keys/hmac.key`）与数据在同一台机器上。能同时取得密钥和写权限的攻击者，可以重算基线与审计链。
3. 如果数据库审计尾部与锚点文件**同时**被截断，又没有带外记录的链头，本地无法检出（TC-R18-N3 演示了这一边界）。请定期用 `pacs audit head` 导出链头并另行保存。
4. 基线对象是 B **收到的网络数据集字节**。入库前（设备端、传输途中）发生的变化 B 无法发现；B 也没有、不声称拥有设备源文件的 File Meta。
5. “指纹一致”只说明与入库时相同，不说明临床内容正确（例如设备录错患者）。
6. 系统无法确定篡改者身份。报告中的“最后一次合法访问记录”和“文件修改时间”只是线索，后者来自操作系统，不可信。
7. 隔离区（`runtime/data/quarantine`）本身没有完整性监控。
8. GUI 的“操作员”只记录、不认证；本期没有登录和 RBAC。
9. 审计中可能包含患者姓名等信息（C-FIND 查询键），真实部署需要做访问控制。

## C. 实现层面的已知问题与风险
0. **（独立复核后修复，2026-11-12）** Codex 复现的两个问题已修复，回归用例见 `tests/test_independent_review_fixes.py`，证据见 `process/independent-review/`：
   - ① 基线 JSON 损坏 / 缺失时核查中断 → 现报告 BASELINE_TAMPERED，单实例隔离（VERIFY_ERROR）；
   - ② 提交后锚点写入失败时出现“索引指向不存在文件” → 现补偿撤销并返回 0xA701，锚点降级期间入库暂停，恢复后自动补锚。

   剩余边界：
   - 降级窗口内的记录在补写前没有锚点保护；
   - 撤销事务本身也失败时（双重故障），实例会以“已入库、锚点待补”的一致状态保留，同时返回 0xA701；
   - 并发写同一新序列时，撤销会保留仍有子项的层级行并改设 origin，这一分支只有代码审查，没有专门的自动化用例（E0）；
   - 锚点降级期间入库暂停，属于可用性上的取舍。
1. **依赖 pynetdicom 内部方法**：准入用 ACSE 子类覆盖 `_negotiate_as_acceptor`；异常影像阻断依赖“发送占位数据集时抛异常 → 计为失败子操作”的行为。版本已锁定在 3.0.4，升级前必须重跑 TC-R2 / TC-R3 / TC-R16。
2. **0xA801 有两种含义**：目的地未登记，或已登记但连不上（pynetdicom 行为）。审计中可区分，但对端从状态码看不出区别。
3. 取回标识符无效时，C-MOVE 会先与**已登记的**目的地建立关联，再返回 0xA900（pynetdicom 处理器协议的限制）。
4. 调阅前校验每次都会读完整文件并计算哈希；大检查的取回延迟随之增加（原型数据量下可以接受）。
5. 周期扫描默认关闭（`periodic_scan_minutes = 0`）；只有手动核查和调阅前校验会发现变化。两次核查之间的变化要到下次核查或调阅时才能发现。
6. 数据库使用进程内单连接加锁；GUI 若另开进程，依赖 SQLite WAL 实现并发读，写入时可能短暂等待。
7. `test_pending_delay_s` 是仅供测试使用的节流参数（让 C-CANCEL 用例可以重复），生产必须为 0。
8. 删除、更正、患者合并本期不支持（D17）；错误的入库只能由管理员在系统之外处理，并且会被核查判定为异常。
9. 一次 uv 自动下载 Python 3.12.14 的尝试在 `%APPDATA%\uv\python` 留下了未完成的安装（创建次版本链接失败），项目最终改用已有的 Python 3.12.14 解释器。该目录可由用户自行清理，不影响本项目。

## D. 过程风险
1. 所有需求默认值都**未经医院客户（信息科 / 影像科）确认**；评审时可能需要推翻（原型可以推倒重来）。
2. 学员号、姓名、组员、个人贡献都是占位，需要用户本人填写；不得由 AI 代填。
